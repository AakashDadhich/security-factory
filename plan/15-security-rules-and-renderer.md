# 15. Security rules and renderer

## Goal
Write the factory's security rules once, as neutral plain-text files, and render them deterministically into `CLAUDE.md` and `AGENTS.md` for a given platform, ASVS level and set of threat-model mitigations. These are the base layer of secure code generation.

## Inputs
- `plan/PROGRESS.md`
- From chunk 01: the `rules/` folder and the package layout

## Tasks
1. Write the neutral rule files in `rules/`, in Markdown with a small YAML front matter (`id`, `applies_to: [web|macos|ios|all]`):
   - `base.md`: the current OWASP Top 10 edition (check owasp.org and use the latest published list), written as do/don't rules.
   - `secure-defaults.md`: parameterised queries only; context-aware output encoding; strict allowlist input validation at every trust boundary; least-privilege permissions; vetted libraries for authentication, sessions and cryptography (never hand-rolled); no secrets in code; `.env.example` with fake values only; dependencies pinned by lockfile.
   - `web.md`: security headers (CSP, HSTS, X-Content-Type-Options, frame-ancestors), CSRF protection for cookie sessions, session cookies `HttpOnly`/`Secure`/`SameSite`, rate limiting on auth endpoints, no stack traces in responses.
   - `apple.md`: Keychain for secrets (`kSecAttrAccessibleWhenUnlockedThisDeviceOnly` or stricter), never UserDefaults for secrets, App Transport Security on with no arbitrary loads, minimal entitlements, App Sandbox and hardened runtime on macOS, privacy manifest with required-reason APIs declared, CryptoKit not CommonCrypto MD5/SHA1.
2. Add the ASVS requirements data: fetch the latest released OWASP ASVS (5.x) machine-readable export from the official `OWASP/ASVS` repo at a pinned tag, keep only id, text, chapter and level, and store it as `rules/asvs/asvs.json` with its source URL, tag and CC BY-SA attribution in `rules/asvs/SOURCE.md`.
3. Write the renderer `factory/rules.py`, run as `python -m factory.rules render --platform <p> --asvs-level <1|2|3> [--threats security/threats.json] --target <claude|agents> --out <file>`. The output contains:
   - a fixed header ("Generated by the security factory; do not edit by hand"),
   - the base, secure-defaults and platform rules,
   - the ASVS requirements up to and including the level, grouped by chapter,
   - a "Project-specific mitigations" section listing each open threat's mitigations from `threats.json` (id, text, ASVS refs).
   `claude` and `agents` targets differ only in the header and file name. Output is byte-for-byte deterministic: sorted, with no timestamps.
4. Add `python -m factory.rules checklist --asvs-level <n> --out <file>`, a JSON checklist used by the second-agent review (chunk 20).
5. Tests: snapshot tests for web L2 and ios L3 output; level filtering (an L3-only requirement is absent at L2); mitigations included; the same inputs give the same bytes.

## Outputs
`rules/base.md`, `rules/secure-defaults.md`, `rules/web.md`, `rules/apple.md`, `rules/asvs/asvs.json`, `rules/asvs/SOURCE.md`, `factory/rules.py`, `tests/test_rules.py`, `tests/snapshots/rules-*.md`.

## Done when
- Selftest is green, including the snapshot and determinism tests.
- `python -m factory.rules render --platform web --asvs-level 2 --target claude --out /tmp/CLAUDE.md` (run in CI, with the output uploaded as an artifact or printed) contains the sections Base, Secure defaults, Web and ASVS L1+L2, and no L3-only ids.
- `rules/asvs/SOURCE.md` names the pinned ASVS tag and the licence.

## Background

### From the design document
> "A security rules file for Claude Code: a project instruction file that bakes in the OWASP Top 10, the ASVS requirements for the chosen level, and the specific mitigations from this project's threat model. Recommended base layer."

> "Secure-by-default patterns: the rules file mandates parameterised queries, output encoding, strict input validation, least-privilege permissions, and vetted libraries for authentication and cryptography rather than hand-rolled versions."

> "Platform extras: for iOS and macOS, rules covering Keychain use, App Transport Security, entitlements and sandboxing; for web, rules covering security headers, CSRF protection and session handling."

> "Keep each stage's prompt, and the shared security rules, as ordinary text files in the factory repo, not inside one tool's private config."

> "Claude's CLAUDE.md file then becomes just one rendering of those neutral rules, generated from them. The AGENTS.md convention, which several coding tools read, can be another."

### Decisions that apply
- D1: ASVS is the primary framework. D2: Level 2 by default, raised to 3 by risk, never lowered.
- D5: the rules file and secure-by-default patterns are both in use.

### Factory facts (shared by every chunk)
- The factory is one public GitHub repo, `AakashDadhich/security-factory` (a personal account, no organisation; see D21), checked out at `/Users/aakash/Documents/projects/secure-software-factory`. One factory serves every project: iOS, macOS and web apps.
- The orchestrator is plain deterministic Python, not an AI. AI runs only inside specific stages, always through the model adapter `python -m factory.adapter`. Prompts and rules are plain text files in the factory repo.
- Repo layout: `factory/` (Python 3.12 package), `prompts/`, `rules/`, `schemas/`, `semgrep-rules/`, `tools/versions.lock`, `Makefile`, `tests/`, `docs/`, `.github/workflows/factory.yml` (the reusable pipeline, `on: workflow_call`), `.github/workflows/selftest.yml` (the factory's own tests), `.github/actions/` (composite actions), `templates/project/`.
- Make targets are thin wrappers around `python -m factory.<module>`. Tests are pytest and run in `selftest.yml` on GitHub. Don't install tools on the owner's Mac. Verify by pushing (after asking) and reading CI results with `gh run view`.
- Runners: GitHub-hosted only. `ubuntu-24.04` for everything except Apple build stages, which use `macos-15`.
- Tools are installed on runners with `python -m factory.tools install <name>`, which reads the exact version, URL and SHA-256 or container digest from `tools/versions.lock` and refuses a mismatch. Third-party actions are pinned by full commit SHA.
- Pipeline jobs check out the factory at `inputs.factory-ref` into `.factory/` and then use `./.factory/.github/actions/setup-factory`.
- Stage contract: each stage writes to `out/<stage>/`: `findings.json` (an array of findings matching `schemas/finding.schema.json`), plus raw SARIF 2.1.0 or CycloneDX JSON where relevant. The job uploads `out/<stage>/` as artifact `<stage>`.
- Finding fields (schema defined in chunk 03): `id`, `stage`, `tool`, `source` (`scanner`, `ai-review`, `ai-threat-model` or `check`), `rule_id`, `title`, `severity` (`critical`, `high`, `medium`, `low` or `info`), `location` (`{path, start_line, end_line}` or `{url, method}`), `cwe` (list), `description`, `remediation`, `fingerprint` (stable across runs).
- Workflow security: top-level `permissions: {}`, and each job grants only what it needs. AI jobs get `contents: read` and never the GitHub App key. Never put `${{ github.event.* }}` text directly into a `run:` script; pass it through `env:`.
- Owner conventions: Conventional Commits; no em dashes in anything written; no code comments unless genuinely non-obvious; tests for all new logic; ask before any push, repo creation or GitHub settings change.
